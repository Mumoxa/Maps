# AGENTS.md — Development Standards for SA Credit Risk Market Map

## Project Overview

- **Stack:** Vite + React 18 + TypeScript + React Router 6 + @xyflow/react
- **Hosting:** GitHub Pages at `https://mumoxa.github.io/Maps/`
- **Base path:** `/Maps/` (set in vite.config.ts and BrowserRouter basename)
- **Deployment:** Push to `main` triggers GitHub Actions workflow that builds and deploys via `actions/deploy-pages`

## Build & Run

```bash
npm install
npm run dev      # local dev server
npm run build    # production build (includes 404.html copy for SPA routing)
```

## Known Architecture Decisions

- Data files (profiles.json, companies.json, etc.) are statically imported and bundled by Vite — not fetched at runtime
- The `gh-pages` branch contains built output and is deployed by GitHub's built-in Pages workflow
- The `dist/` directory is generated by the build and must NOT be committed to git

## Mandatory Rules

These rules apply to every change in this codebase. Violations must be fixed before merge.

### 1. Never commit build artifacts or dependencies

`dist/`, `node_modules/`, and `*.tsbuildinfo` must be in `.gitignore` and never tracked. Every new project starts with a `.gitignore` before the first commit.

### 2. Always configure base paths for the target host

Before writing deployment config, determine the base URL. Set `base` in vite.config.ts and `basename` on BrowserRouter. Verify the deployed build actually loads in a browser — a green CI pipeline does not mean the site works.

### 3. No debugging leftovers

Never commit `|| true`, `&& false`, `if (true)`, `if (false)`, `console.log`, or dead statements like `SomeType as any` on their own line. Use proper feature flags if you need to bypass logic temporarily.

### 4. Derive data, never hardcode it

- Counts (profiles, companies, segments) must come from the data at runtime, not hardcoded strings
- Duplicate detection must be algorithmic, not name-matching against hardcoded strings
- Alias/normalization mappings belong in a config file, not inline in business logic
- If a function accepts a `data` parameter, it must actually use it

### 5. Use O(1) lookups, not O(n) searches in loops

- Build `Map<id, entity>` and `Map<slug, id>` indexes once during data loading
- Never use `.find()` or `.filter()` inside `.map()`, `.sort()`, or render loops
- Never convert a Map to an array to search by value — build a reverse map instead
- Pre-compute derived values (company profile counts, segment counts) rather than filtering on every render

### 6. One utility, one location

Search the codebase for existing implementations before writing a new helper. Duplicate utility functions (e.g., two different `slugify` implementations) produce inconsistent output and routing bugs.

### 7. Keyboard accessibility is required

- Every interactive element must be keyboard-accessible
- Use semantic HTML (`button`, `a`) instead of `div`/`span` with `onClick`
- Add `role`, `tabIndex`, and `onKeyDown` when semantic HTML isn't possible
- Add `:focus-visible` styles — zero focus styles in the CSS is not acceptable
- Test with Tab key before shipping

### 8. Use CSS classes, not inline styles

- If a style appears more than once, extract it to a CSS class
- Inline styles are only for truly dynamic values (computed widths, positions)
- Hardcoded hex colors must use CSS custom properties
- Never copy-paste identical style objects across components

### 9. No dead code or unused imports

- Enable `noUnusedLocals` and `noUnusedParameters` in tsconfig
- Remove dead code branches, unused variables, and unreachable statements
- If `useEffect` dependencies change the source data, internal state must sync — stale state from initial render is a bug

### 10. Responsive design is required

- Design mobile-first with at least three breakpoints (mobile, tablet, desktop)
- No fixed-width elements that overflow on small screens
- Test on actual device widths before shipping

## PR Checklist

Before merging any PR, verify:

- [ ] `.gitignore` covers build artifacts (`dist/`, `node_modules/`, `*.tsbuildinfo`)
- [ ] No `|| true`, `console.log`, or debugging leftovers
- [ ] No hardcoded counts, names, or data that should be derived
- [ ] No `.find()` or `.filter()` inside loops — use Maps for lookups
- [ ] No duplicate utility functions
- [ ] All interactive elements are keyboard-accessible with focus styles
- [ ] No copy-pasted inline styles — CSS classes used instead
- [ ] Linter passes with zero warnings
- [ ] The deployed build actually loads in a browser
- [ ] Responsive at mobile, tablet, and desktop widths
- [ ] TypeScript strict mode passes with no errors
